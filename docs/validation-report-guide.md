# Validation Report Guide

This guide explains how to interpret the repository validation outputs generated by:

```text
python3 tools/generate_validation_report.py
```

The command produces two local artifacts:

```text
status/generated-status.json
status/validation-report.md
```

## Generated status

`status/generated-status.json` is the machine-readable output. It is intended for CI, task runners, and ecosystem management.

Important fields:

| Field | Meaning |
| --- | --- |
| `repo` | Repository identity. |
| `status_version` | Version of the generated status format. |
| `state` | Overall validation state, usually `self-check-pass` or `self-check-fail`. |
| `goal_activation_percent` | Current goal activation estimate. |
| `full_build_percent` | Current full-build estimate for the active goal. |
| `handoff_ready` | Whether downstream systems can treat the repo as ready for handoff. |
| `checks` | Ordered validation checks and their structured results. |
| `remaining` | Remaining hardening items. |

## Validation report

`status/validation-report.md` is the human-readable output. It is intended for reviewers and maintainers.

The report summarizes:

- repository identity;
- current state;
- goal activation percent;
- full-build percent;
- handoff readiness;
- each validation command;
- pass/fail state for each validation command;
- problem counts;
- remaining hardening items.

## Current checks

The validation report is generated from the same checks used by `tools/generate_status.py`.

| Check | Purpose |
| --- | --- |
| `tools/assess_repo.py` | Confirms required repository files exist. |
| `tools/validate_schema_files.py` | Confirms schema files are parseable JSON objects with required top-level schema structure. |
| `tools/validate_examples.py` | Confirms example JSON files are parseable and contain required fields. |
| `tools/validate_by_schema_subset.py` | Validates positive fixtures against the supported dependency-free schema subset. |
| `tools/validate_negative_fixtures.py` | Confirms invalid fixtures are rejected for expected reasons. |
| `tools/check_evaluator_fixture.py` | Confirms evaluator output matches expected ALLOW, DENY, and FAIL-CLOSED fixtures. |

## Passing state

A passing state means:

```text
state = self-check-pass
handoff_ready = true
```

A passing state does not certify external ARA artifacts. It only means this repository's local fixtures, schemas, evaluator stub, and validation/reporting path are internally coherent under the current dependency-free validation policy.

## Failing state

A failing state means one or more validation checks returned a non-zero exit code.

Use the `checks` array in `status/generated-status.json` to identify:

- which command failed;
- the command return code;
- machine-readable stdout, when available;
- stderr output;
- problem counts and problem details.

## Boundary

This validation path does not replace full JSON Schema validation. It intentionally avoids external dependencies unless the project later adopts a dependency policy.

Future hardening may add a stricter optional path using a full JSON Schema implementation.
